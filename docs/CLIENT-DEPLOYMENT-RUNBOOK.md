# ASODITECH — Client Deployment Runbook

Step-by-step guide for onboarding a **new client**, from zero to
production. Written for a developer who has never deployed this project
before. Every technical claim here is sourced from the actual codebase
(file paths and ADRs cited throughout) — nothing is invented. Companion
documents:

- `docs/CLIENT-ENVIRONMENT-VARIABLES.md` — the full environment-variable
  table (purpose / source / example / secret-or-public / required-or-optional).
- `docs/SHARED-VS-DEDICATED.md` — the architecture and diagrams behind
  §7 below.
- `docs/CLIENT-HANDOVER-CHECKLIST.md` — the final sign-off checklist.
- `.env.production.example` — a fillable template of every variable below.
- `docs/adr/*.md` — the engineering decision record for everything cited
  here as "(ADR NNNN)."

**Maintenance contract**: `tests/lib/deployment-docs-coverage.test.ts`
fails `pnpm test` if a new environment variable is added to
`src/lib/env.ts` (or another documented runtime-config source) without a
matching entry in `.env.production.example` and
`docs/CLIENT-ENVIRONMENT-VARIABLES.md`. It cannot enforce prose accuracy
elsewhere in this file — when you change deployment architecture (a new
integration, a new migration risk, a new required manual step), update
this runbook by hand in the same PR, the same discipline
`docs/CONTRIBUTING.md` already requires for the in-app Documentation
Center.

## 0. Before you start — pick a model

Read `docs/SHARED-VS-DEDICATED.md` first. Short version:

- **Shared SaaS**: add the client as a `Tenant` on your existing shared
  Vercel + Supabase deployment via `/platform` → skip straight to §8.
- **Dedicated**: the client gets their own Vercel project, own Supabase
  project, own domain → follow §1 through §12 in order.

The rest of this runbook is written for the **Dedicated** path end to end
(it is the more complete path — a Shared-SaaS onboarding is a strict
subset of it, called out inline).

## 1. Client account creation

### Recommended ownership model

Create every third-party account **under the client's own identity**, not
yours — this avoids a painful account-transfer process later and matches
`docs/CLIENT-HANDOVER-CHECKLIST.md`'s ownership expectations.

1. **A dedicated Google/Gmail account for the client**, if they don't
   already have a suitable one (e.g. `contact@theirdomain.com` via Google
   Workspace, or a plain Gmail if they have no existing Workspace). This
   account will own:
   - Their Vercel account (Vercel supports "Continue with Google").
   - Their Supabase account (also supports Google sign-in).
   - The Google Cloud project for Drive-backup OAuth, if they want that
     feature.
2. **Vercel**: created under the client's Google/email account, you added
   as a **Member** (not Owner) on the project/team for the duration of
   setup and any ongoing support agreement.
3. **Supabase**: same pattern — client's own account owns the
   organization/project, you're added as a collaborator.
4. **Domain**: must already be owned by the client, or purchased by them
   directly at a registrar of their choice. Never register a client's
   production domain under your own personal account (see the handover
   checklist's ownership table).

### Credentials that must NEVER be shared with you

- The client's Vercel/Supabase/domain-registrar **account passwords**.
  Access as a Member/collaborator never requires the password.
- Their Google account's own password (only OAuth consent is needed for
  the Drive backup feature — see §5).
- Any external platform's admin password (WooCommerce wp-admin, Shopify
  admin login) — you only ever need API credentials (a Consumer
  Key/Secret, an Admin API access token), generated *by them*, from
  *their* admin panel, and pasted into this app's Intégrations page.

### Credentials you DO need temporarily during installation

- Vercel: Member access to the project (via an invite you accept).
- Supabase: collaborator access to the project (via an invite you accept).
- Enough access to the client's DNS provider to add the records Vercel's
  domain screen asks for (or the client adds them themselves while you
  watch/guide).
- WooCommerce/Shopify/carrier API credentials, generated by the client's
  own staff in their own admin panels, handed to you (or entered directly
  by them) only long enough to paste into this app's connection forms —
  they are encrypted at rest (`INTEGRATION_ENCRYPTION_KEY`,
  `src/lib/crypto.ts`) the moment they're saved, and this app never
  exposes them back to the browser afterward (every connect action
  returns only `{ id }`, per `docs/adr/0004`'s audit addendum).

## 2. Vercel setup

### 2.1 Create the project

1. In the client's Vercel account/team: **Add New… → Project**.
2. **Connect the Git repository** — this codebase, on the branch you want
   as production (typically `main`).
3. **Framework preset**: Vercel auto-detects Next.js — leave it.
4. **Production branch**: `main` (Vercel default) — change only if the
   client's workflow uses a different long-lived branch name.

### 2.2 Build settings

Leave the Build Command on Vercel's default. `package.json` defines:

```json
"build": "next build",
"vercel-build": "prisma migrate deploy && next build",
"postinstall": "prisma generate"
```

Vercel automatically runs `vercel-build` instead of `build` when a
`vercel-build` script exists — no manual Build Command override is
needed, though you may set it explicitly to `pnpm vercel-build` for
clarity. This means **every production deployment runs `prisma migrate
deploy` against the production database before building** — see §6
(Database migrations) for the real risk this creates and how to manage it
safely.

`postinstall` runs `prisma generate` with no database connection required
(`prisma.config.ts` falls back to a placeholder URL specifically so
`pnpm install` never needs `DATABASE_URL` to succeed).

**Package manager**: `package.json` pins `"packageManager": "pnpm@9.12.0"`
— Vercel detects and uses pnpm automatically from `pnpm-lock.yaml` and
this field; no configuration needed.

**Node.js version**: this project is developed against Node 24 and
requires **Node 20.9+** (`README.md`) — set this explicitly under
Project → Settings → General → Node.js Version if the client's Vercel
account defaults to an older version.

### 2.3 Environment variables

Project → Settings → Environment Variables. Set every variable from
`docs/CLIENT-ENVIRONMENT-VARIABLES.md` for **both** the Production and
Preview environments (Preview matters because `vercel-build` runs `prisma
migrate deploy` there too — see the critical warning in §6). At minimum,
before the first deploy can succeed:

- `DATABASE_URL`, `DIRECT_URL`, `AUTH_SECRET`, `INTEGRATION_ENCRYPTION_KEY`
  — `next build` fails while collecting routes without all four
  (`src/lib/env.ts` validates them at import time).
- `APP_URL` — has a wrong default (`localhost:3000`) if left unset.

Add the optional ones (`RESEND_API_KEY`/`EMAIL_FROM`,
`BACKUP_ENCRYPTION_KEY`, `GOOGLE_OAUTH_CLIENT_ID`/`_SECRET`,
`SHOPIFY_INTEGRATION_ENABLED`) once you reach the corresponding
integration in §5, or up front if you already know the client needs them.

`NODE_ENV` is set by Vercel automatically per environment — never add it
by hand.

### 2.4 Domain configuration

1. Project → Settings → Domains → add the client's domain.
2. Vercel shows the DNS records to add (an `A` record to Vercel's IP, or
   a `CNAME` for a subdomain) — add these in the client's own DNS
   provider.
3. Wait for "Valid Configuration" — Vercel issues and auto-renews the SSL
   certificate once DNS validates. This is fully automatic; no manual
   certificate step exists.
4. Update `APP_URL` to the final `https://` domain and redeploy (or
   trigger a redeploy — env var changes don't apply to an already-running
   deployment).

### 2.5 Region

`vercel.json` pins `"regions": ["fra1"]` (Frankfurt) for serverless
function execution — this applies to every deployment of this codebase
unless overridden. Combined with Supabase's own region choice (§3), pick
both to minimize latency to the client's actual user base; for a
Morocco-based client, `fra1` (or a Supabase EU region) is a reasonable
default, but confirm this deliberately rather than assuming it's
optimal for every client — changing it means editing `vercel.json` in the
deployed branch.

### 2.6 First deployment & verification

1. Trigger the deploy (push to the production branch, or "Deploy" in the
   Vercel dashboard).
2. **This first deploy will run `prisma migrate deploy` against an
   otherwise-empty database** — confirm `DATABASE_URL`/`DIRECT_URL`
   already point at a real, reachable Postgres database (§3) before
   triggering it, or the build fails at the migration step.
3. Watch the build log for the `vercel-build` step — you should see
   Prisma applying all 31 migrations (`prisma/migrations/`), followed by
   a normal `next build`.
4. Once deployed, before doing anything else: run the RLS provisioning
   step (§3.5) and the first-admin seed (§8) — the app is not usable
   (and not safely multi-tenant-isolated) until both are done.
5. Open the deployed URL and confirm the login page renders.

### 2.7 Rollback procedure

Vercel keeps every previous deployment. To roll back the **application
code**: Project → Deployments → find the last known-good deployment → "…"
menu → **Promote to Production**. This is instant and does not re-run
`vercel-build` (it reuses the already-built artifact).

**Rolling back a deployment does NOT roll back a database migration.**
If the deployment you're rolling back away from included a schema
migration, promoting an older deployment gives you old application code
talking to a *new* schema — this can break in subtle ways (a column the
old code doesn't expect, a column the old code needs that no longer
exists). See §6.5 for the real database-rollback story; a Vercel
"rollback" alone is only safe when the deployment being undone made no
schema change.

## 3. Supabase setup

(Any Postgres provider works in principle — `DATABASE_URL`/`DIRECT_URL`
are generic connection strings — but this codebase's own docs
(`.env.example`, `docs/adr/0001-tech-stack.md`, `docs/adr/0026`) are
written against Supabase specifically, so this section follows that.)

### 3.1 Create the project

1. In the client's Supabase account: **New Project**.
2. **Region**: pick the region closest to the client's actual users/the
   Vercel region chosen in §2.5 — cross-region latency between Vercel's
   functions and the database directly affects every request, and this
   app opens at least one extra round trip per request once RLS is
   enabled (§3.4's performance note).
3. Set a strong database password (this becomes part of `DIRECT_URL`) —
   store it in the client's password manager, not only in your own.
4. Wait for provisioning to complete.

### 3.2 Connection strings

Project Settings → Database → Connection string:

- **`DIRECT_URL`** = the direct/session connection (port 5432), using the
  **postgres** (owner) role. Used only for `prisma migrate deploy`.
- **`DATABASE_URL`** = the pooled connection (port 6543, "Transaction"
  pooler mode / PgBouncer), with `?pgbouncer=true` appended — required so
  Prisma disables prepared statements, which don't survive
  transaction-pooling mode (`.env.example`'s own comment). This is the
  one the running app uses for every request — but **not** yet with the
  owner role; see §3.5.

### 3.3 Run migrations

From your own machine, pointed at the new database:

```bash
DIRECT_URL="<the owner/direct connection string>" \
DATABASE_URL="<same, or the pooled string — only DIRECT_URL matters here>" \
npx prisma migrate deploy
```

(In practice this first run typically happens automatically as part of
§2.6's first Vercel deploy — this manual invocation is for verifying
connectivity ahead of time, or for re-running deploy from your machine if
you ever need to.)

### 3.4 Row-Level Security — already defined, must be verified active

Every tenant-scoped table already has Postgres RLS `ENABLE`d and
`FORCE`d by migration `20260907150000_row_level_security`
(`docs/adr/0026-multi-tenant-rls.md`) — **this ships automatically with
`prisma migrate deploy`, no separate step needed for the policies
themselves.** What does *not* ship automatically, and is the single most
important production-readiness step in this entire runbook, is §3.5
below.

### 3.5 The restricted runtime role (do this before real data exists)

RLS enforces **nothing** for a superuser or for the table owner — and the
owner role is exactly what `DIRECT_URL`/Supabase's default `postgres`
role is. If the deployed app's `DATABASE_URL` connects as that same owner
role, every RLS policy in the database is silently inert.

1. Connect to the database as the owner role (the same one `DIRECT_URL`
   uses):

   ```bash
   psql "<owner connection string, direct port 5432>" \
     -v app_role=asoditech_app \
     -v app_password="'REPLACE_WITH_A_STRONG_RANDOM_PASSWORD'" \
     -v migration_role=postgres \
     -f scripts/provision-production-role.sql
   ```

   Confirm `migration_role` matches whatever role actually ran `prisma
   migrate deploy` in this environment (`SELECT current_user;` over
   `DIRECT_URL` if unsure — on Supabase this is normally `postgres`).
   This script is idempotent — safe to re-run later if a future migration
   needs it re-applied for a different `migration_role`.

2. **Update `DATABASE_URL` in Vercel** (Production **and** Preview) to
   use `asoditech_app` (or whatever `app_role` you chose) with its real
   password, instead of the owner role. `DIRECT_URL` stays on the owner
   role — migrations still need DDL rights the restricted role
   deliberately lacks.

3. **Verify RLS is actually active** — do not skip this, and do not trust
   that step 1 alone was enough:

   ```bash
   APP_ROLE_URL="postgresql://asoditech_app:<password>@<host>:5432/<db>" \
     ./scripts/verify-rls.sh
   ```

   This script is safe to run directly against production: every check
   runs inside one transaction that always `ROLLBACK`s, so nothing it
   creates (including two scratch tenants/users) is ever committed. It
   must connect on the **direct** port as the **restricted** role (not
   pooled, not the owner) and prints `PASS`/`FAIL` for each of several
   adversarial checks (a query with no tenant context set sees zero rows,
   a cross-tenant write is rejected, etc.). **Do not consider an
   environment production-ready until every line prints `PASS`.**

4. Redeploy (or wait for the next deploy) so the app picks up the new
   `DATABASE_URL`.

### 3.6 Authentication

This app does **not** use Supabase Auth — it has its own hand-rolled
session system (`src/lib/auth/session.ts`, opaque HMAC-hashed tokens in
an httpOnly cookie, `docs/adr/0003-auth-and-rbac.md`). No Supabase
Authentication configuration is required or used. Supabase is used purely
as a managed Postgres instance.

### 3.7 Storage

This app stores **no files in Supabase Storage or any object store**.
Everything it persists lives in Postgres rows — `Product.imageUrl`-style
fields are plain URL strings the operator supplies (e.g. from an external
image host), never an upload pipeline. There is no S3/R2/Supabase Storage
integration anywhere in the codebase to configure.

### 3.8 Backups (infrastructure level)

Enable Supabase's own automatic database backups (Settings → Database →
Backups; availability and retention depend on the client's Supabase
plan). This is independent of, and complementary to, this app's own
tenant-scoped Backup & Portability module (§5's "Google Drive / Backup"
integration, `docs/adr/0034`) — the Supabase-level backup protects
against catastrophic database loss and is operator-only/whole-database;
the in-app module gives a tenant a portable, secret-free copy of just
their own data. Both should exist; neither substitutes for the other
(explained in `docs/adr/0034`'s own "Context" section).

### 3.9 Production checks before go-live

- [ ] `prisma migrate deploy` has run cleanly (§3.3 / §2.6).
- [ ] The restricted runtime role exists and `DATABASE_URL` uses it, not
      the owner role (§3.5 step 2).
- [ ] `scripts/verify-rls.sh` prints all `PASS` against this database
      (§3.5 step 3).
- [ ] `DIRECT_URL` still uses the owner role (needed for future
      migrations).
- [ ] Supabase's own automatic backups are enabled (§3.8).
- [ ] The database region matches or is close to the Vercel region
      (§2.5/§3.1).

## 5. Integrations

General pattern across every real integration in this app: credentials
are entered through the app's own UI (never a Vercel environment
variable — those are for *this app's* own configuration, not a tenant's
external accounts), encrypted at rest with `INTEGRATION_ENCRYPTION_KEY`
(`src/lib/crypto.ts`, AES-256-GCM), and never returned to the browser
once saved. Every connection has an honest four-state lifecycle
(`IntegrationStatus` / the equivalent field on `ShippingProvider`):
`DECONNECTE` (never configured / disconnected) → `CONFIGURE` (credentials
saved, not yet verified) → `CONNECTE` (a real "Tester la connexion"
request actually succeeded) → `ERREUR` (the last test or sync failed).
**Saving credentials never implies a working connection** — always click
"Tester la connexion" and confirm the badge turns green before relying on
an integration.

### 5.1 WooCommerce (fully real — `docs/adr/0010-woocommerce-integration.md`)

- **Credentials, from the client**: WooCommerce admin → Réglages →
  Avancé → REST API → Ajouter une clé, permissions "Lecture/Écriture."
  Copy the Consumer Key and Consumer Secret.
- **In this app**: Intégrations → WooCommerce → Configurer → paste the
  store URL (HTTPS only — HTTP stores are rejected outright, no OAuth
  1.0a fallback is implemented) + key/secret → Enregistrer. No
  environment variable is involved; nothing to set in Vercel.
- **Test**: click "Tester la connexion" — this is the only action that
  can set status to `CONNECTE` (a real `GET /orders?per_page=1` request).
- **Initial sync**: "Synchroniser les produits" then "Synchroniser les
  commandes." "Pousser le stock" sends current internal sellable stock
  back to WooCommerce for already-linked products (a separate, explicit,
  one-shot action — never automatic, never bidirectional in the same
  run).
- **Webhooks** (optional, for near-real-time order import): click
  "Générer un secret webhook" in this app, then in WooCommerce admin →
  Réglages → Avancé → Webhooks, create two webhooks — topics "Commande
  créée" and "Commande mise à jour" — pointing at
  `https://<your-domain>/api/webhooks/woocommerce`, pasting in the
  generated secret. This URL is **the same for every tenant** on a shared
  deployment; the app disambiguates which tenant/store a webhook belongs
  to by testing the HMAC signature against every stored WooCommerce
  `Integration` row (`docs/adr/0025` §1) — never from anything in the
  webhook payload itself.
- **Failure symptoms**: a failed connection test shows a French, safe
  error message (never a raw exception/response body/URL —
  `docs/adr/0010` "Error handling") and sets status `ERREUR` +
  `lastError`. A webhook whose signature doesn't match any stored secret
  is rejected with HTTP 401 and audited against `"unknown"` (no
  integration can be blamed for a request that matched nothing). A sync
  with partial item failures lands the `SyncRun` on `PARTIEL`, never a
  false "success."
- **Disconnect/reconnect**: "Déconnecter" on the integration card
  (`disconnectIntegrationAction`) — safe to do at any time; reconnecting
  is the same Configurer flow above, generating a new webhook secret if
  webhooks are wanted again (the old WooCommerce-side webhook
  registration should be deleted or updated in WooCommerce admin
  manually — this app does not manage the WooCommerce webhook resource's
  lifecycle, by design, per `docs/adr/0010` "Webhooks").
- **Known limitation**: only the first WooCommerce category maps to this
  app's single `categoryId`; no real live-store acceptance test was
  performed during development (no live credentials were available) — the
  adapter is fixture-tested, not yet production-battle-tested against a
  real store at the time of writing.

### 5.2 Shopify (fully real, but **disabled by default**)

- **Deployment-wide kill switch**: `SHOPIFY_INTEGRATION_ENABLED` must be
  the literal string `"true"` in Vercel's Environment Variables for this
  client's deployment, or Shopify shows as "Bientôt disponible" and
  refuses every connect/configure/sync action (existing connections still
  receive webhooks regardless — `src/lib/integrations/shopify/feature-flag.ts`).
  This was a deliberate product decision (client feedback #10), not a
  bug — confirm with the business owner whether this client should have
  it enabled before flipping it on.
- **Credentials, from the client**: an existing Shopify **custom app**'s
  Admin API access token (new custom apps can no longer be created from
  the classic Shopify admin — use the Shopify Dev Dashboard/CLI). Needs
  at minimum `read_products`, `read_inventory`, `read_orders` scopes, plus
  `write_inventory` only if stock-push is wanted.
- **In this app**: Intégrations → Shopify → Configurer → shop name (bare
  name or full `*.myshopify.com` — a connected custom domain is
  **rejected**, the Admin API is only ever called at the myshopify.com
  domain) + access token. The "Client secret" field (webhook signing) is
  optional at this step.
- **Test**: "Tester la connexion" (`locations(first: 1)` GraphQL query) —
  only this can set `CONNECTE`.
- **Initial sync**: "Synchroniser les produits" (imports active Shopify
  Locations as `Warehouse` rows, then products/variants with per-location
  stock) then "Synchroniser les commandes." "Pousser le stock" is
  per-location, sellable stock only.
- **Webhooks**: this app does **not** generate the webhook secret for
  Shopify (unlike WooCommerce) — Shopify itself generates the custom
  app's Client secret; enter that same value as this integration's
  webhook secret. In Shopify's custom-app API configuration → Webhooks,
  subscribe to "Order creation," "Order update," "Order cancellation,"
  "Refund creation," pointing at
  `https://<your-domain>/api/webhooks/shopify` — same one-URL-per-deployment
  disambiguation-by-signature model as WooCommerce.
- **Failure symptoms / disconnect**: same pattern as WooCommerce —
  typed, safe error classes; `ERREUR` status with `lastError`; a
  `THROTTLED` GraphQL response (Shopify's cost-based rate limiting, not
  HTTP 429) is retried with backoff automatically up to 3 times before
  surfacing as an error. Disconnect via the same "Déconnecter" action,
  gated **not** by the kill switch (a tenant who connected before the
  flag was flipped off can still cleanly detach).
- **Known limitation**: **not live-verified against a real store at all**
  — every fact in `docs/adr/0011-shopify-integration.md` was verified
  against Shopify's official documentation, not a live account, because
  none was available during development. Treat a new Shopify connection
  as needing careful first-sync review, not a black box.

### 5.3 OzonExpress — Moroccan delivery carrier (real, registered — `docs/adr/0013`)

- **Credentials, from the client**: contact OzonExpress
  (`contact@ozonexpress.ma`) for a merchant account; they provide a
  Customer ID and an API key.
- **In this app**: Livraison → Prestataires → "Nouveau prestataire," type
  **API**, name it, then "Configurer" → choose **OzonExpress (Maroc)** →
  enter Identifiant client + Clé API. Optional JSON config:
  `stockMode` (`"ramassage"` or `"stock"`), `defaultParcelNature`, and a
  `cityIdByName` override map (only needed if OzonExpress's own `/cities`
  catalogue misspells a city the operator wants matched differently).
- **Test**: "Tester la connexion" — calls `GET /cities` (live-verified:
  801 cities with per-city delivery pricing) then an authenticated
  `tracking`/`parcel-info` sentinel lookup (live-verified: real
  authentication confirmed against a real account, id `70275`, read-only).
  This is structurally incapable of creating a real parcel.
- **Delivery cost**: taken directly from OzonExpress's own per-city
  `DELIVERED-PRICE` — never guessed, never defaulted to 0.
- **Known limitations, stated plainly**: **no cancellation endpoint
  exists** (creating a shipment is final on OzonExpress's side); **no
  webhooks** — status only updates via the per-shipment "Synchroniser"
  button (poll-only); **`add-parcel` (actually creating a shipment) has
  NOT been verified against a real parcel** — only read-only endpoints
  (`tracking`, `/cities`) have live confirmation. Advise the client's
  first real shipment be treated as a verification event, and watch it
  closely.
- **Disconnect/reconnect**: "Supprimer" on the provider row (blocked if
  the provider still has any `Shipment` — must reassign/close those
  first); reconnecting is the same Configurer flow with fresh credentials.

### 5.4 Aramex — delivery carrier (real, registered, not live-verified — `docs/adr/0028`)

- **Credentials, from the client**: an Aramex Shipping API account —
  `UserName`, `Password`, `AccountNumber`, `AccountPin`, `AccountEntity`
  (3-letter origin branch, e.g. `CMN` for Casablanca), `AccountCountryCode`.
- **In this app**: Livraison → Prestataires → Configurer → **Aramex** —
  enter the `ClientInfo` fields above, plus the shipper address/contact
  config (`shipperName`, `shipperPhone`, `shipperLine1`, `shipperCity`,
  `shipperCountryCode`) that ships on every created shipment — Aramex
  requires a full shipper address per shipment, and this app stores it
  once at the connector level rather than per order.
- **Sandbox first**: set config `sandbox: true` to route every call to
  Aramex's test environment (`ws.dev.aramex.net`) before touching the
  live host — do this for the client's very first setup regardless of
  whether they'll use sandbox long-term.
- **Test**: "Tester la connexion" runs one `TrackShipments` call against
  an obviously-invalid waybill (`"0000000000"`) — valid credentials
  return `HasErrors: false`; the success message also reports whether the
  shipper address you configured is complete.
- **Known limitations, stated plainly**: **no live shipment has been
  created or tracked through this adapter** — the status-mapping table
  and the exact `CreateShipments` response shape are a best-effort
  reconstruction from Aramex's sample code, not confirmed against a real
  account. **No cancellation** (Aramex's cancel flow is pickup-scoped, not
  waybill-scoped) and **no webhooks** (poll-only, same as OzonExpress).
  Treat this client's first real Aramex shipment as a verification event
  and update `docs/adr/0028` with an addendum once confirmed (the same
  pattern `docs/adr/0013` followed for OzonExpress).
- **Disconnect/reconnect**: same "Supprimer"/"Configurer" pattern as
  OzonExpress.

### 5.5 Google Drive — Backup destination (real, optional — `docs/adr/0034` Phase 2)

- **Setup, once per deployment** (this is a Vercel environment variable,
  not a per-tenant credential — see §2.3):
  1. Google Cloud Console → APIs & Services → enable the **Google Drive
     API**.
  2. OAuth consent screen: External, scopes `drive.file` + `openid` +
     `email`.
  3. Credentials → Create OAuth client ID → **Web application**.
     Authorized redirect URI:
     `https://<your-domain>/parametres/sauvegarde/google/callback`
     (must exactly match `APP_URL`).
  4. Set `GOOGLE_OAUTH_CLIENT_ID` / `GOOGLE_OAUTH_CLIENT_SECRET` in
     Vercel. Unset ⇒ the feature is entirely inert, no error surfaced.
  5. While the consent screen is in "Testing," only explicitly added test
     users can connect — publish it for the client's real users to
     connect their own Drive accounts.
- **Per-tenant connection** (in-app, no further env vars): Réglages →
  Sauvegarde → "Connecter Google Drive" → the tenant's own OAuth consent
  → creates a dedicated `ASODITECH Backups / <tenant-slug>` folder in
  *their own* Drive (scope `drive.file` — this app can never see any
  other file in their Drive).
- **Test**: connecting itself is the verification — a successful OAuth
  callback exchanges and stores tokens; "Pousser vers Drive" performs and
  verifies an actual upload (size + checksum re-verified after upload).
- **Failure symptoms**: an expired/revoked refresh token surfaces as
  connection status `ERREUR` with a "Reconnecter" banner
  (`backup.drive_token_error` audited); a deleted Drive folder is
  silently recreated on the next call; a deleted individual file shows
  "fichier absent de Drive" in the list.
- **Disconnect/reconnect**: "Déconnecter" deletes only the
  `GoogleDriveConnection` row (best-effort token revoke) — local tenant
  data and any already-pushed `DRIVE_EXPORT` records are untouched.
  Reconnecting (even to the same Google account) creates a fresh
  connection; a **different** Google account gets a fresh, empty folder —
  old backups stay in the old account.
- **Not built**: no scheduled/automatic push to Drive — every push is the
  manual "Pousser vers Drive" action (Phase 3 of `docs/adr/0034`, not
  built).

### 5.6 Email — Resend (real, optional — `src/lib/email.ts`)

- **Credentials**: sign up at resend.com, verify the client's sending
  domain, create an API key.
- **In this app**: `RESEND_API_KEY` + `EMAIL_FROM` as Vercel environment
  variables (§2.3) — not an in-app connection form; this is deployment-level
  configuration, shared by every tenant on that deployment (see
  `docs/SHARED-VS-DEDICATED.md`'s "what is genuinely shared" table).
- **What it sends**: invitation emails (new user provisioning), password
  reset emails, and support-widget "signaler un problème" forwards. **No
  other email is sent by this app** — no order-confirmation emails, no
  marketing emails, no digest emails exist in the codebase.
- **Test**: invite a test user (Utilisateurs → Inviter) and confirm the
  email arrives; or trigger a password reset.
- **Failure behavior**: unset ⇒ every send is logged to the server
  console instead (a safe, working fallback — check Vercel's function
  logs if a client reports "I never got the invitation email" and
  confirm these two vars are actually set). A Resend API failure is
  logged and swallowed, never surfaced as an action failure — the
  invitation/reset row is already committed and its link is still
  visible in-app (Utilisateurs page) or in the audit log regardless of
  email delivery.
- **Disconnect/reconnect**: remove the two env vars to fall back to
  log-only; there is no in-app toggle.

### 5.7 WhatsApp — click-to-chat only, NOT an API integration

Despite `IntegrationProvider.WHATSAPP` existing as a schema enum value
(`docs/adr/0004`), **there is no WhatsApp Business API integration built**
— it is listed on the Integrations page as planned/unavailable, same as
every other still-scaffolded provider (Meta Ads, Google Ads, TikTok Ads,
Google Sheets, `AI_PROVIDER`): `connectIntegrationAction` only stores a
site URL and encrypted API key with no adapter behind it.

What genuinely exists and works today is **`wa.me` click-to-chat link
generation** (`src/lib/whatsapp.ts`), used in two places:
- The order confirmation queue (`src/components/orders/confirmation-queue.tsx`)
  — a "WhatsApp" button opens `https://wa.me/<customer number>?text=...`
  with a pre-filled message, using the customer's own `whatsapp`/`phone`
  field.
- The support widget's contact section
  (`src/components/support/support-contact-section.tsx`) — uses
  `BusinessSettings.supportWhatsapp` (Réglages → Entreprise) if set.

Nothing to configure beyond filling in `supportWhatsapp` in Réglages if
the client wants that contact option shown; no credentials, no API, no
webhook.

### 5.8 AI Assistant — controlled tool layer, no LLM (`docs/adr/0009`)

Not an external integration to configure at all, but worth setting
expectations correctly: the "Assistant IA" page presents seven fixed
buttons (revenue this month, net profit, best seller, etc.), each running
one real, typed Prisma query and returning a factual French sentence.
**There is no LLM call anywhere in this codebase** and no free-text
input — the page's own copy says this explicitly. No API key, no
environment variable, nothing to connect. Do not promise a client
conversational AI capability this system does not have.

### 5.9 Not built at all (planned-only, per `docs/adr/0004`)

Meta Ads, Google Ads, TikTok Ads, and Google Sheets each get only
credential storage (`connectIntegrationAction`, lands on `CONFIGURE`,
never `CONNECTE`) with **no adapter, no API call, no import/export, no
configuration UI beyond that generic form**. Do not configure these for a
client expecting real functionality — there is none behind them yet.

## 6. Database migrations

### 6.1 How migrations deploy in production, exactly

`package.json`'s `vercel-build` script is `prisma migrate deploy && next
build` — **every single Vercel deployment**, on every environment that
runs this script (Production and Preview both, by default), applies any
pending migration from `prisma/migrations/` to whatever database
`DIRECT_URL` points at, before building. There is no manual "click to
migrate" step in the normal flow — pushing code that includes a new
migration *is* the deploy trigger.

### 6.2 Critical risk: Preview using the Production database

**Nothing in this codebase's Vercel configuration prevents a Preview
deployment's `DIRECT_URL`/`DATABASE_URL` from pointing at the production
database.** If you set Preview's environment variables to the same
values as Production (easy to do by accident, since Vercel's "apply to
all environments" checkbox defaults to on when adding a variable), then
**every pull-request preview deploy runs `prisma migrate deploy` against
production** the moment it's opened. This is a real, currently-live
configuration on this project's own Vercel deployment as of this audit
(Preview's `DATABASE_URL` is the production database) — treat it as a
live, standing risk on any deployment using this codebase, not a
hypothetical, and confirm/fix it explicitly for every new client project
rather than assuming Vercel's defaults are safe.

**Safe production workflow, recommended:**

1. **Provision a genuinely separate Preview/staging database** — a second
   Supabase project (even a free-tier one) is the cleanest option — and
   point Preview's `DATABASE_URL`/`DIRECT_URL` at *that*, never at
   Production's.
2. If a separate database is truly not feasible for this client (cost,
   simplicity), at minimum **do not open Preview deployments (pull
   requests) against schema-changing branches** without first confirming
   Preview's env vars — check Project → Settings → Environment Variables,
   confirm `DATABASE_URL`/`DIRECT_URL` differ between Production and
   Preview rows, every single time a new environment is set up.
3. Before merging any PR that includes a new `prisma/migrations/`
   directory, review the migration SQL by hand (`git diff` on the new
   `migration.sql` file) — this codebase's own migrations are frequently
   hand-written rather than pure Prisma-diff output specifically to avoid
   destructive default behavior (e.g. `docs/adr/0027`'s `RENAME VALUE`
   instead of a drop-and-recreate for an enum rename) — a migration that
   looks like a plain `DROP COLUMN`/`DROP TABLE` deserves a second look
   before it reaches production.

### 6.3 Automatic `prisma migrate deploy` — what it will and won't do

- It applies pending migrations in order, records them in Prisma's
  `_prisma_migrations` table, and **fails the whole build** if any
  migration errors (schema drift, a `DO $$ RAISE EXCEPTION $$` guard
  tripping, a constraint violation against real data) — the deployment
  does not go live, and the previous deployment keeps serving traffic.
  This is a safety property, not a bug: a broken migration blocking
  deploy is strictly better than a partially-applied schema serving
  requests.
- It does **not** run `scripts/provision-production-role.sql` or
  `scripts/verify-rls.sh` — those are one-time, manual, per-environment
  steps (§3.5) that migrations deliberately never automate (they need a
  password, which does not belong in migration history).
- It does **not** re-seed data — `prisma/seed.ts` is a separate, manual
  command (§8), never run automatically on deploy.

### 6.4 Migration failure — what to do

1. Check the Vercel build log for the exact Prisma error.
2. If it's a genuine schema conflict (e.g. the target database already
   has manual, out-of-band changes) — do **not** attempt to hand-edit
   `_prisma_migrations` on production without first taking a full
   database snapshot/backup (Supabase's point-in-time recovery or a
   manual `pg_dump`, depending on plan).
3. If it's a bug in the migration SQL itself — fix it in a **new**
   migration (never edit an already-committed migration file that may
   have partially applied elsewhere), test it against a fresh clone of
   production data locally first, then redeploy.
4. The previous deployment remains live throughout — there is no
   automatic rollback of a failed migration attempt within the same
   `migrate deploy` run for a single failed statement wrapped in its own
   transaction (Prisma runs each migration file's statements
   transactionally where the DDL allows it), but always verify the
   actual state of `_prisma_migrations` and the schema after any failure
   rather than assuming a clean rollback occurred.

### 6.5 Rollback of a migration already applied

**There is no automatic "undo migration" tooling in this codebase.**
Rolling back a schema change that has already been applied to production
means either:
- Writing and applying a new, forward migration that reverses the
  change (preferred — keeps the migration history linear and honest), or
- Restoring the database from a backup taken before the migration ran
  (Supabase point-in-time recovery, or a `pg_dump` you took manually) —
  which also rolls back **every other write** since that backup, business
  data included. Only acceptable for a genuine emergency, and only after
  confirming with the client.

### 6.6 Data migrations

Every existing migration in `prisma/migrations/` that needed to backfill
data (the multi-tenant `tenantId` backfill in `docs/adr/0023`, the
`SALES`→`CONFIRMATION` enum rename in `docs/adr/0027`, etc.) does so
**inside the same hand-written `migration.sql`**, using `UPDATE`
statements and `DO $$ ... $$` guard blocks that `RAISE EXCEPTION` if the
backfill didn't fully succeed — never a silent partial state. There is no
separate "data migration" tool or script pattern beyond this. If a future
change needs a genuinely large backfill (a full-table rewrite at real
production scale), consider whether it needs to run outside the build's
migration step entirely (a one-off script run manually, like
`scripts/backfill-tenant-baseline.ts`) rather than inside `vercel-build`,
which has Vercel's build-time limits to respect.

### 6.7 Backups before risky migrations

Before deploying any migration that drops a column/table, changes a
column's type, or renames something load-bearing:

1. Take a manual backup — either Supabase's own snapshot feature, or a
   full `pg_dump` you control directly, **in addition to** whatever
   automatic backup schedule Supabase's plan provides (§3.8) —
   automatic backups may not run frequently enough to give you a
   recovery point immediately before this specific change.
2. If the client has real business data and the migration is
   destructive, consider also taking a Backup & Portability `.asb`
   export (Réglages → Sauvegarde, §5.5) as a secondary, human-readable
   copy of at least their tenant-scoped data — faster to eyeball than a
   raw `pg_dump`, though it deliberately excludes credentials/sessions
   (§5.5, `docs/adr/0034`).
3. Test the migration against a clone of production data locally first
   whenever the change touches a table with real rows — every
   multi-tenant-phase ADR in this codebase (0023, 0025, 0026, 0027)
   explicitly verified its migration against "a production-shaped clone"
   before being accepted; follow the same discipline for any new
   migration you write.

## 8. First admin / owner

Exact process, from real code (`prisma/seed.ts`, `docs/adr/0027-tenant-provisioning.md`):

### 8.1 Dedicated deployment — first (and only) tenant

Run once, from your own machine, pointed at the production database
(**never** as part of the automatic Vercel build):

```bash
DATABASE_URL="<prod DIRECT_URL — needs the owner role for this bootstrap, see prisma/seed.ts>" \
SEED_OWNER_EMAIL="owner@client-domain.com" \
SEED_OWNER_PASSWORD="<a real, strong, unique password>" \
pnpm exec tsx prisma/seed.ts
```

- `SEED_OWNER_PASSWORD` is **required** whenever `NODE_ENV=production` —
  the script throws and refuses to run without it, specifically to
  prevent seeding the one `isPlatformAdmin: true` account with the
  well-known local default password (`change-me-immediately`, sitting in
  source control).
- The script is idempotent (`upsert`) — safe to re-run; it never
  overwrites an existing user's password or creates duplicate business
  data.
- This creates: the bootstrap `Tenant` (`id: "default"`), one `OWNER`
  user with `isPlatformAdmin: true`, the default warehouse, the
  `BusinessSettings` singleton row, and the standard expense categories.
  **Zero customers, products, or orders** — an empty dashboard
  immediately after is correct, not a bug.
- Hand the email/password to the client through a secure channel (never
  plain email/Slack) and have them log in and change the password
  immediately — there is no forced first-login password-change flow in
  the codebase, so this is a process discipline, not an enforced one.

### 8.2 Shared SaaS deployment — adding a new tenant

The bootstrap tenant and its OWNER already exist on a shared deployment
(created once, when that deployment was first stood up, via §8.1). Adding
a **new client** to it:

1. Log in as an existing **platform admin** (`isPlatformAdmin: true` —
   today, only the bootstrap tenant's OWNER has this by default; granting
   it to anyone else is a direct database update, since there is no
   in-app UI to promote a platform admin — `docs/adr/0027` builds no such
   UI).
2. Go to `/platform` (its own route group, separate chrome from the
   regular tenant-scoped app).
3. Use the "Nouveau tenant" form (`CreateTenantForm` →
   `createTenantAction`) — creates the `Tenant` row **and** an OWNER-role
   `Invitation` for it in one action.
4. The invitation is emailed via `sendInvitationEmail`
   (`src/lib/email.ts`) if `RESEND_API_KEY`/`EMAIL_FROM` are configured
   for this deployment — otherwise the link is logged server-side and you
   must relay it manually.
5. The invitee clicks the link, sets their own password, and becomes that
   new tenant's first OWNER. There is no admin-chosen initial password
   anywhere in this flow (`createUserAction` was deliberately removed —
   `docs/adr/0027` §2) — every account, including a tenant's first, is
   created only by accepting an invitation.
6. From there, that tenant's own OWNER/ADMIN invites their own teammates
   (Utilisateurs → Inviter) — you do not need platform-admin access for
   ongoing user management within a tenant you're not operating.

### 8.3 Every subsequent user, in either model

Invitation-only, always: Utilisateurs → "Inviter un utilisateur" (OWNER or
ADMIN, `users.manage` permission) → email + role → an `Invitation` row
(7-day TTL, single-use) is created and emailed (or logged, if email isn't
configured). The invitee sets their own password on acceptance. Forgotten
passwords: "Mot de passe oublié" on the login page
(`requestPasswordResetAction`) — always returns the same generic response
regardless of whether the email matched anything, and issues a real,
emailed (or logged) reset link with a 1-hour TTL; an OWNER/ADMIN can also
trigger a reset directly for a user they manage
(`adminResetPasswordAction`, `users.manage`) and relay the link
themselves.

## 9. Production checklist

- [ ] **Domain**: added to Vercel, "Valid Configuration," `APP_URL`
      matches exactly.
- [ ] **SSL**: certificate issued (Vercel automatic) — confirmed in a
      browser.
- [ ] **Environment variables**: all four required vars set for both
      Production and Preview (§2.3); Preview points at a **separate**
      database, not production (§6.2) — verified, not assumed.
- [ ] **Database**: `prisma migrate deploy` applied cleanly (§3.3/§6.1);
      Supabase automatic backups enabled (§3.8).
- [ ] **Migrations**: no pending/failed migration in the Vercel build log
      for the current production deployment.
- [ ] **Authentication**: login works with a real account; session cookie
      (`aec_session`) is `httpOnly`/`secure` in production (automatic,
      `src/lib/auth/session.ts` — verify via browser dev tools on the
      live domain, not localhost).
- [ ] **RLS**: `DATABASE_URL` uses the restricted runtime role, not the
      owner (§3.5 step 2); `scripts/verify-rls.sh` prints all `PASS`
      against this database (§3.5 step 3) — **do not skip this.**
- [ ] **Permissions**: the first OWNER account logged in successfully and
      can see the expected role-appropriate navigation
      (`docs/adr/0003`'s role table).
- [ ] **Integrations**: every integration this client actually needs is
      `CONNECTE` (green), not merely `CONFIGURE` (§5) — check each one's
      badge, don't assume saving credentials means it works.
- [ ] **Webhooks**: for any connected WooCommerce/Shopify store expecting
      near-real-time orders, the webhook is registered on the external
      platform's side and a real test order/update has been confirmed to
      arrive.
- [ ] **Backups**: `BACKUP_ENCRYPTION_KEY` set and backed up outside the
      database (§4/env-vars doc); at least one manual `.asb` backup taken
      and downloaded successfully.
- [ ] **Cron/background jobs**: **none exist in this codebase** — no
      Vercel Cron configuration (`vercel.json` only sets `regions`), no
      queue, no scheduler. Every sync, backup, and reconciliation action
      is user-triggered. If the client needs a recurring action (a
      nightly stock sync, a scheduled backup), it must be built or
      arranged externally (e.g. an external cron hitting a Server Action
      via an authenticated request) — not assumed to exist.
- [ ] **Error monitoring**: **not implemented in this codebase** — no
      Sentry, no `@vercel/analytics`/`@vercel/speed-insights`, no error
      tracking package of any kind. The only observability today is
      Vercel's own Function Logs (Project → Logs/Observability) and
      whatever `console.log`/`console.error` calls happen to run.
      Strongly recommend adding a real error-monitoring integration (see
      §12) as an operational follow-up, especially before a client with
      real revenue goes live.
- [ ] **Logs**: confirm Vercel's Function Logs are actually reachable to
      whoever will operate this deployment day to day (project access,
      not just your own).
- [ ] **Performance**: Vercel region and Supabase region are close to
      each other and to the client's real users (§2.5/§3.1); a basic page
      load and a representative order-list page have been eyeballed for
      obviously-wrong latency.
- [ ] **Security**: `AUTH_SECRET`/`INTEGRATION_ENCRYPTION_KEY`/
      `BACKUP_ENCRYPTION_KEY` are unique to this deployment (never
      copy-pasted from another client's — see §13); no credential appears
      in `git log`/committed files (`.env*` are gitignored, confirmed);
      the restricted RLS role is confirmed non-superuser/`NOBYPASSRLS`
      (`scripts/provision-production-role.sql`'s own sanity-check query).
- [ ] **Test order**: create one real order end to end (manual creation,
      or via a real WooCommerce/Shopify sync) and progress it through the
      confirmation/delivery flow.
- [ ] **Test delivery**: create one shipment via whichever carrier this
      client uses and confirm status sync ("Synchroniser") works — for
      OzonExpress/Aramex specifically, treat the very first real shipment
      as a live-verification event (§5.3/§5.4).
- [ ] **Test backup**: a manual backup was generated and downloaded
      successfully (§5.5/§9's Backups item above).
- [ ] **Test restore**: a restore was actually performed at least once
      (ideally against a disposable/staging tenant, not production) and
      confirmed to work, including confirming every integration correctly
      shows disconnected afterward and was successfully reconnected.

## 11. Troubleshooting

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| **Vercel build failure** at `next build` | A genuine TypeScript/lint/build error in the deployed code, or a required env var missing (`src/lib/env.ts` throws `"Invalid environment variables"` at import time, listing which). | Read the exact Vercel build log error. If it's the env-var throw, check all four required vars (§2.3) are set for the environment that failed (Production vs. Preview are configured independently). |
| **Vercel build failure** at `prisma migrate deploy` (inside `vercel-build`) | A migration failed against the target database — schema drift, a data-integrity guard (`DO $$ RAISE EXCEPTION $$`) tripping, or `DIRECT_URL` pointing at an unreachable/wrong database. | See §6.4. Check `DIRECT_URL` is correct and reachable from Vercel's network (Supabase allows this by default; a custom Postgres provider may need an IP allowlist that includes Vercel's egress). |
| **Prisma migration failure** specifically citing a constraint violation on real data | A migration assumes a data shape that doesn't hold for this client's existing rows (rare for a fresh Dedicated deployment; more likely on a long-lived Shared deployment with unusual historical data). | Do not force it through. Inspect the actual offending rows via `DIRECT_URL` with `psql`, decide the correct backfill, write a follow-up migration — never hand-edit a migration file already applied elsewhere. |
| **Database connection failure** (app can't reach Postgres at runtime, not at build) | `DATABASE_URL` wrong/unreachable, Supabase project paused (free tier auto-pauses after inactivity), or the pooled connection is missing `?pgbouncer=true`. | Confirm the connection string in Supabase's dashboard matches Vercel's env var exactly; resume the project if paused; confirm `pgbouncer=true` is present. |
| **RLS failure** — a user sees another tenant's data, or (more likely if something's misconfigured) sees **no** data that should be theirs | `DATABASE_URL` is connecting as the table owner/a superuser (RLS is inert for those, §3.5), or `scripts/verify-rls.sh` was never run against this environment. | Run `scripts/verify-rls.sh` immediately. If any check fails, `DATABASE_URL` is not using the restricted role — fix per §3.5 before doing anything else; treat this as a security incident if real cross-tenant data exposure is suspected, not just a bug. |
| **Authentication failure** — can't log in with known-correct credentials | `AUTH_SECRET` was changed/rotated (invalidates every session, but should not affect the ability to log in fresh with the correct password — if login itself fails, check `User.status` is `ACTIVE` and the tenant's `status` is `ACTIVE`, not `SUSPENDED`, since `docs/adr/0027` §5 makes a suspended tenant's login rejected immediately). | Check the user's `status` and their `Tenant.status` directly in the database if the UI gives no clue; check `AUTH_SECRET` is set consistently (an app restart with a *different* `AUTH_SECRET` than what signed existing session cookies invalidates them all, which looks like "suddenly logged out," not "can't log in at all"). |
| **Wrong environment variables** (generic) | A value pasted with extra whitespace/quotes, a Preview/Production mismatch, or a variable set for the wrong environment. | Re-check the exact variable against `docs/CLIENT-ENVIRONMENT-VARIABLES.md`'s example format; confirm which Vercel environment(s) it's set for; redeploy after any change (env var edits don't retroactively apply to an already-running deployment). |
| **WooCommerce webhook failure** (orders not arriving in near-real-time) | Wrong URL registered, wrong/rotated secret, or the webhook topic isn't "Commande créée"/"Commande mise à jour." | Re-check the exact URL (`https://<domain>/api/webhooks/woocommerce`) and secret in WooCommerce admin against what "Générer un secret webhook" produced; a signature mismatch is a silent 401 from this app's side — check Vercel Function Logs for that route. Manual "Synchroniser les commandes" always works as a fallback regardless of webhook health. |
| **Shopify webhook failure** | `SHOPIFY_INTEGRATION_ENABLED` is off (webhooks for an *existing* connection still process, but a *new* connection can't be configured at all while disabled), wrong Client secret entered as the webhook secret, or the wrong topics subscribed. | Confirm the feature flag first if this is a new setup. Otherwise same signature-debugging approach as WooCommerce, on `/api/webhooks/shopify`. |
| **Google OAuth failure** (Drive connect fails at the consent screen or callback) | OAuth consent screen still in "Testing" and this user isn't an added test user; redirect URI mismatch; `GOOGLE_OAUTH_CLIENT_ID`/`_SECRET` unset or wrong. | Confirm the exact redirect URI registered in Google Cloud matches `${APP_URL}/parametres/sauvegarde/google/callback` byte-for-byte (including https/no trailing slash); publish the consent screen for general users if this is a real client, not just internal testing. |
| **Google Drive failure** (connected, but push/restore fails) | Refresh token revoked (shows `ERREUR` + "Reconnecter" banner), Drive API quota, or the app-created folder was deleted in Drive. | Reconnect if the banner shows; the app-created folder is recreated automatically on the next call if deleted — no action needed beyond retrying. A persistent 403 usually means the OAuth consent scope was changed/revoked at the Google account level — reconnect. |
| **Slow application** | Vercel/Supabase region mismatch (cross-region round trips add up, especially with RLS's extra per-request transaction — see §14); a large, unoptimized report query; Supabase connection pool exhaustion under load (next symptom). | Check region alignment first (§2.5/§3.1) — it's the cheapest fix and the most common cause. For a specific slow page, check the relevant `src/lib/queries/*.ts` file for an obviously unbounded query. |
| **Database connection exhaustion** (errors under concurrent load, especially with several tenants active at once) | Postgres/Supabase has a hard connection limit; every top-level Prisma call not already inside a transaction opens its own short transaction under RLS (§3.4/`docs/adr/0026`'s documented performance tradeoff — "more round trips per request" is an accepted, known cost), which multiplies connection churn under load. Serverless functions also each hold their own connection(s), and Vercel can scale to many concurrent function instances. | Confirm `DATABASE_URL` uses the **pooled** (6543/PgBouncer) connection, not the direct one — using the direct connection at any real concurrency is a common, avoidable cause of exhaustion. If pooled and still exhausting, this is a genuine scaling signal — see §14; consider Supabase's connection pooler settings/plan tier, or (per §7) migrating this client to a dedicated deployment if they're the sole cause. |
| **API rate limiting** — Shopify `THROTTLED`, WooCommerce 429, a carrier's own limit | Normal under a large sync or many concurrent syncs; each adapter already retries with backoff (§5.2/§5.1) up to a few attempts. | If it persists past the adapter's own retry budget, it's usually a genuinely large one-time sync (first import of a big store) — retry the sync action after a short wait; there is no built-in scheduling/queueing to spread this out automatically. |
| **Domain/SSL issue** | DNS not yet propagated, or the wrong record type/target was added. | Re-check Vercel's Domains screen for the exact record it expects; DNS propagation can take up to 48 hours in rare cases though usually far less; Vercel will not issue a certificate until DNS validates. |

## 12. Operations — maintaining a deployed client

- **Updates**: push to the production branch (`main`, by default) to
  deploy new application code. Vercel builds and deploys automatically;
  the previous deployment stays available for instant rollback (§2.7) as
  long as no migration accompanied the change you're rolling back.
- **Migrations**: ship with application code, applied automatically by
  `vercel-build` (§6). Review every new migration's SQL by hand before
  merging, especially anything touching a table with real client data —
  there is no staging-gate automation beyond your own review and, if
  configured (§6.2), a genuinely separate Preview database.
- **Monitoring**: **no dedicated tool exists today** (§9's checklist item
  above). At minimum, periodically check Vercel's Function Logs for
  recurring errors. Recommended, not yet built: add a proper error
  tracker (e.g. Sentry) and a basic uptime check external to Vercel
  itself — neither requires a schema change, both are additive
  `next.config.ts`/dependency changes.
- **Backups**: manual, per client, via Réglages → Sauvegarde — there is
  no automatic schedule (§5.5, §9). If this client needs recurring
  backups, either commit to a manual cadence (a calendar reminder) or
  treat building Phase 3 of `docs/adr/0034` (scheduled backups +
  retention) as a prerequisite before promising "automatic backups" to
  any client.
- **Incident response**: for anything touching cross-tenant data
  exposure, treat `scripts/verify-rls.sh` failing as the first diagnostic
  step (§11's RLS row) — this is the single highest-severity class of bug
  this architecture can have. For data loss, the recovery order is: the
  in-app Backup module's `PRE_RESTORE_SNAPSHOT` (if the incident followed
  a restore), then the client's own last `.asb` backup, then Supabase's
  infrastructure-level backup/point-in-time-recovery as the last resort
  (whole-database, not tenant-scoped — affects every tenant on a shared
  deployment).
- **Rollback**: application code via Vercel's "Promote to Production"
  (§2.7); schema via a new forward migration or a full database restore
  (§6.5) — never assume the former undoes the latter.
- **Security updates**: this project has no automated dependency-update
  tooling configured in-repo (no Dependabot/Renovate config found) —
  treat `pnpm outdated` / manual review of `package.json` as a periodic,
  manual task, particularly for `next`, `prisma`, `@prisma/client`, and
  `bcryptjs`. Rotate `AUTH_SECRET` if a session-token compromise is ever
  suspected (invalidates every live session, forcing re-login — not
  disruptive to data). Never rotate `INTEGRATION_ENCRYPTION_KEY` or
  `BACKUP_ENCRYPTION_KEY` without a plan for what happens to
  already-encrypted data (there is no re-encryption tool — rotating
  either key orphans everything encrypted under the old one).

## 13. Client-specific configuration

### Configurable per tenant, without any code change

All of `BusinessSettings` (Réglages → Entreprise), one row per tenant:
`companyName`, `currency` (default `MAD`), `address`/`city`/`country`,
`phone`/`email`, `logoUrl`, `timezone` (default
`Africa/Casablanca`), `locale` (default `fr`),
`lowStockDefaultThreshold`, `orderNumberPrefix`, and the support-widget
contact fields (`supportName`, `supportWhatsapp`, `supportPhone`,
`supportEmail`, `supportHours`). Also fully per-tenant: every integration
connection (§5), every `ShippingProvider`, the RBAC role assignments for
that tenant's own users, and (Shared SaaS only) the tenant's own `slug`
and lifecycle `status` (`ACTIVE`/`SUSPENDED`, via `/platform`).

### Currently global that should eventually become tenant-specific

- **`SHOPIFY_INTEGRATION_ENABLED`** — a single deployment-wide flag. On a
  Shared SaaS deployment, this means Shopify is either on for *every*
  tenant sharing that deployment or off for all of them — there is no way
  to enable it for one tenant only today. A genuine gap if a Shared
  deployment ever needs mixed Shopify availability across its tenants.
- **`RESEND_API_KEY`/`EMAIL_FROM`** — one sending identity for every
  tenant's transactional email on a shared deployment. A tenant cannot
  send invitations "from" their own domain without either a dedicated
  deployment or a future per-tenant email-sending feature.
- **`INTEGRATION_ENCRYPTION_KEY`/`BACKUP_ENCRYPTION_KEY`** — one key
  protects every tenant's secrets on a deployment. Acceptable for the
  Shared model as designed (the RLS/application-layer isolation is what's
  supposed to prevent one tenant from ever reading another's encrypted
  blob in the first place), but worth naming explicitly as a shared blast
  radius if that key is ever compromised.
- **The domain itself (`APP_URL`)** — inherent to the Shared model (one
  deployment, one domain); not a gap so much as the defining tradeoff
  `docs/SHARED-VS-DEDICATED.md` names.
- **Vercel region (`vercel.json`)** — one region for every tenant on a
  deployment; a tenant far from that region has no per-tenant way to get
  closer without a dedicated deployment.

## 14. Scaling

Based on the actual architecture — no load testing has been performed in
this codebase; the following is architectural reasoning from what's
actually built, not measured benchmarks.

- **1 client (Dedicated, or the only tenant on a Shared deployment)**:
  the baseline case every ADR was verified against. RLS adds a documented
  but small per-request cost (an extra `SET LOCAL` + query inside one
  transaction instead of one autocommit statement, per
  `docs/adr/0026`'s "Performance tradeoff, accepted for this exercise").
  No bottleneck expected at normal e-commerce-back-office traffic levels.
- **10 clients** (Shared SaaS, 10 `Tenant` rows on one deployment, or 10
  independent Dedicated deployments): for Shared, this is still well
  within a small Supabase plan's connection-pool limits; for Dedicated,
  this is just "10 independent instances of the 1-client case" — no new
  bottleneck class, only linear infrastructure cost.
- **50 clients on one Shared deployment**: the pooled `DATABASE_URL`
  connection count (§11's connection-exhaustion row) becomes a real
  planning input — every tenant's concurrent user activity draws from
  the same Postgres connection pool. This is the point at which
  Supabase's pooler configuration/plan tier (pool size, max client
  connections) needs deliberate sizing, not defaults. A single noisy
  tenant (a large WooCommerce/Shopify sync, a heavy report) is felt by
  the other 49 (§13's "Currently global" list is also fully in effect at
  this scale — one shared Resend account's rate limits, one shared
  encryption key's blast radius).
- **100 clients on one Shared deployment**: the architecture has **no
  built-in usage isolation** between tenants beyond RLS's data isolation
  — no per-tenant rate limiting, no per-tenant resource quota, no queue to
  smooth out a burst (§9's "no cron/background jobs" applies here too:
  every sync is synchronous and user-triggered, competing for the same
  serverless function concurrency and database pool as every other
  tenant's simultaneous action). At this scale, actively monitor
  connection-pool saturation and consider splitting the largest/noisiest
  tenants onto Dedicated deployments (`docs/SHARED-VS-DEDICATED.md`'s
  Hybrid model) rather than scaling the shared pool indefinitely.
- **500 clients**: almost certainly requires the Hybrid model in practice
  (`docs/SHARED-VS-DEDICATED.md` §C) — several Shared deployments
  segmented by client tier/size, or a genuine background-job
  infrastructure (queues, scheduled workers) that does not exist in this
  codebase today for sync/backup/report work. The Backup module's own
  `docs/adr/0034` explicitly names "background-job generation for
  tenants past the synchronous caps" (100,000 rows / 25 MiB per backup)
  as future, unbuilt work — a suffiently large tenant's backup/restore
  already hits a hard synchronous ceiling well before 500-client scale is
  reached.

### What to upgrade first, in order

1. **Supabase connection pooling configuration/plan tier** — the first
   thing to hit a wall as concurrent tenant count grows, and the cheapest
   to fix (a plan upgrade or pooler tuning, no code change).
2. **Split out the largest/noisiest tenants to Dedicated deployments**
   (Hybrid model) — before building shared-infrastructure scaling
   features, this is usually cheaper and immediately available with the
   architecture as it exists today.
3. **A real background-job system** (queue + worker) for sync/backup/report
   work that currently runs synchronously inside a request/Server Action
   — a genuine architecture addition, needed before either very large
   individual tenants or very high shared-tenant-count scale.
4. **Error monitoring and per-tenant usage visibility** (§9/§12) — not a
   scaling fix by itself, but a prerequisite for knowing *which* tenant
   or code path to blame once problems start at scale, since none exists
   today.

## 15. Business / platform readiness audit

Explicit audit of commercial/platform features — **what exists vs. what
is missing**. Nothing in this section is implemented as part of this
task; it is a status report only.

| Capability | Status | Detail |
| --- | --- | --- |
| Subscription plans | ❌ Not implemented | No `Plan`/`Subscription` model anywhere in `prisma/schema.prisma`. Every tenant has identical, unlimited access to every feature. |
| Feature entitlements | ❌ Not implemented | No per-tenant feature-flag or entitlement table. The one feature toggle that exists, `SHOPIFY_INTEGRATION_ENABLED`, is a deployment-wide env var, not a tenant entitlement (§13). |
| Usage limits | ❌ Not implemented | No rate limiting, no row-count quota, no seat limit anywhere in application code. The Backup module's `MAX_TOTAL_ROWS`/`MAX_CONTAINER_BYTES` (`docs/adr/0034`) are safety ceilings for that one module's synchronous processing, not a business usage limit. |
| Tenant-specific feature flags | ❌ Not implemented | See §13 — the only runtime flag (`SHOPIFY_INTEGRATION_ENABLED`) is deployment-wide, not per-tenant. |
| Usage metering | ❌ Not implemented | No event/usage-tracking table; `SyncRun`/`AuditEvent` exist for operational/audit purposes, not billing metering, and are not aggregated anywhere for that purpose. |
| Client suspension | ✅ Implemented | `Tenant.status` (`ACTIVE`/`SUSPENDED`), `suspendTenantAction`/`activateTenantAction` (`docs/adr/0027` §5, platform-admin only). Suspension is immediate and hard: every session for every user of that tenant is destroyed in the same action, and `getCurrentUser()` independently re-checks tenant status on every request so a session created in the narrow gap before revocation is still rejected. The bootstrap tenant (`id: "default"`) can never be suspended. |
| Trial periods | ❌ Not implemented | No trial/expiry date field on `Tenant`, no automatic downgrade or lockout tied to time. |
| Billing states | ❌ Not implemented | No `paymentStatus`/`billingStatus` concept at the tenant level (note: `Order.paymentStatus` exists, but that is a customer order's payment state within the e-commerce domain, unrelated to the tenant's own subscription/billing relationship with you). |

**Summary**: this codebase is a full-featured e-commerce back-office with
genuine multi-tenant data isolation (`docs/adr/0023`-`0027`), but **zero
SaaS commercial/billing infrastructure**. The only lever available today
to control a client's access is binary: `Tenant.status` active or
suspended. Any pricing tiers, feature gating, or usage-based billing
promised to a client must currently be enforced entirely **outside** this
codebase (a manual process, or a separate billing system you build/buy)
— do not represent any of the ❌ rows above as available when
scoping a client engagement.

`tests/lib/deployment-docs-coverage.test.ts` fails the suite if
`src/lib/env.ts` (or the other documented runtime-config sources) gains a
new variable that isn't reflected in `.env.production.example` and

the in-app Documentation Center's own equivalent guardrail,

files this section names — nothing will stop a PR that skips it. That
test cannot verify prose
accuracy elsewhere in this file — when deployment architecture changes
(a new integration, a new migration risk, a newly-built background-job
system, a monitoring tool finally added), update the relevant section of
this runbook, `docs/SHARED-VS-DEDICATED.md`, and/or
`docs/CLIENT-HANDOVER-CHECKLIST.md` in the same PR, following the same
discipline `docs/CONTRIBUTING.md` already establishes for the in-app
Documentation Center: **a deployment-relevant change is incomplete until
this runbook reflects it.**
