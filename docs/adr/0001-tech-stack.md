# ADR 0001 — Tech stack

## Status
Accepted (2026-08-21)

## Context
The repository was empty. This is the first product built on this stack —
ASODITECH E-commerce Management System — and it will eventually run as a
licensed `Instance` under the ASODITECH Control Center (see
`../../ASODITECH Control Center/asoditech control center`, a sibling
repository on this machine). That project made and documented a set of
stack decisions eleven months into this account's life; rather than
re-litigate them, this project adopts the same stack for consistency across
ASODITECH products maintained by the same team, and because the Control
Center's own ADRs already justify each choice in detail.

## Decision
- **Framework:** Next.js 16 (App Router), TypeScript, React 19.2 — same
  reasoning as Control Center ADR 0001: one deployable app for admin UI +
  Server Actions + the future licensing check-in client, first-class SSR
  for an internal-facing dashboard. Next.js 16 conventions differ from most
  training data (`middleware.ts` → `proxy.ts`, fully-async
  `params`/`searchParams`/`cookies()`/`headers()`) — `AGENTS.md` at the repo
  root (generated by `next dev`) points at the bundled docs.
- **Database:** PostgreSQL. This system tracks orders, payments, and stock
  — relational integrity (foreign keys, unique constraints, enums) is not
  optional here.
- **ORM:** Prisma, pinned to **6.19.2** — same reasoning as Control Center:
  Prisma 7's generator/config changes aren't yet reflected in common
  tooling knowledge; revisit once that upgrade is well-understood.
- **Auth:** hand-rolled, database-backed sessions (see
  `docs/adr/0003-auth-and-rbac.md`) — this system additionally needs
  granular RBAC across eight operational roles, which the Control Center's
  simpler OWNER/ADMIN model didn't need.
- **Validation:** Zod v4 at every Server Action boundary and in
  `src/lib/env.ts`.
- **UI:** Tailwind CSS v4 + shadcn/ui (`base-nova` style, `@base-ui/react`,
  not Radix) — component source copied and extended from the Control
  Center's own `src/components/ui/` where identical, hand-built for the
  primitives that project didn't need (checkbox, switch, popover, tooltip,
  sheet, skeleton, breadcrumb, command palette, scroll-area). `lucide-react`
  for icons, `recharts` for the Analytics/Finance charts (the one dependency
  this project needed that Control Center didn't).
- **Testing:** Vitest against a real local Postgres test database
  (`asoditech_ecommerce_test`), not mocks — same reasoning as Control
  Center: business-rule tests (state machines, stock arithmetic, financial
  calculations) need a real database to be trustworthy.
- **Password hashing:** `bcryptjs`.
- **Hosting/production database:** not yet decided for this specific
  client deployment — the schema's `DATABASE_URL`/`DIRECT_URL` split
  (pooled vs. direct) is ready for the same Vercel + Supabase pattern
  Control Center uses, but this is a decision for the operator at deploy
  time, not baked into the code.

## Consequences
- No Docker in this environment; local Postgres runs via Homebrew
  (`postgresql@16`), already running when this project was scaffolded.
- Same upgrade discipline as Control Center: Prisma 7, Next 17, etc. are
  deliberate migrations, not routine `pnpm update`.
- Reusing Control Center's UI primitives verbatim where they're generic
  (button, dialog, table, select, etc.) means a future design change to
  one product's `src/components/ui/` won't automatically propagate to the
  other — there is no shared package. Acceptable for two products; revisit
  (extract a shared UI package) if a third ASODITECH product needs the same
  design system.
